# 技术决策与可验证契约

当前方案采用 **Vue 3、TypeScript、Vite 和 HTML/CSS**。纯 TypeScript 模拟内核供 Web Worker 与无界面验证共用，Dexie 封装 IndexedDB。目标交付是可从本地启动或静态托管的游戏、设备本地存档和可导入导出的文件。文字由已结算的事实生成，运行时无需在线模型。N0 建立项目并锁定兼容版本。首个贯通场景是随机招徒、正式入门绑定、向一名宿主发布私令并在达成当刻发奖。[玩法依据](gameplay.md) · [当前工单](roadmap.md#m1-开工单)

## 为什么采用这套组合

| 候选 | 对这个项目的收益 | 代价与决定 |
| --- | --- | --- |
| Vue 3 / React | 双方均能把候选名帖、私人任务、可变长度战报和归来摘要表达成响应式 DOM。浏览器负责中文换行、焦点、缩放和滚动。 | 选 Vue 单文件组件，将表意模板、排版及交互就地维护。状态真相在内核，每个小步无需驱动所有人物组件刷新。若团队以后有实测瓶颈，先量消息／布局成本。[Vue](https://vuejs.org/guide/introduction.html) · [React](https://react.dev/learn/thinking-in-react) |
| 原生 DOM + TypeScript | 依赖最少，适合已留存的静态排版校样。 | 长期维护人物筛选、回归摘要、多层钻取与焦点恢复需要手工同步，切片起使用 Vue。 |
| PixiJS | 适合未来大量动态图元、地图或局部高密度演出。 | 首版一张插画、少量头像与偶尔一张图集，CSS 足够。需求出现后只对该图层比较 Canvas2D 与 Pixi 的真机成本。[PixiJS](https://pixijs.com/8.x/guides/getting-started/intro) |
| Phaser / Three.js | Phaser 提供完整二维游戏循环。Three.js 擅长空间场景。 | 首版几乎没有连续场景交互，文字输入、可访问性、长纪事与移动排版仍要 DOM。多维护一套坐标、输入与渲染循环的收益很低。[Phaser](https://docs.phaser.io/phaser/getting-started/what-is-phaser) |

### 模块边界

| 建议目录 | 拥有的数据和接口 | 谁可以改变世界 |
| --- | --- | --- |
| `src/sim/` | 候选与成员身份、宿主绑定、修为与技艺、宗门库存、任务和奖账、道源与道统根基。保留 `advance(state, untilTick, orderedCommands)` 边界，输出新状态与有序事实。 | 只接受合法命令及到期行动，独立于 DOM、网络和墙钟 |
| `src/content/` | 招募地域与人选权重，任务目标、条件、明奖与隐藏奖，以及功法、技艺、环境和文字规则。 | 内容引用有定义的条件和效果，并明确影响宿主、宗门库存或系统资源。文案只描述已经发生的事 |
| `src/worker/` | 接收 `AdvanceTo / SubmitCommand / QueryHistory`，管理排序、分段推进、持久化与取消。 | 同一存档单写，广播 `revision + viewDelta`。主线程只取可见人物和分页事实。 |
| `src/storage/` | 存档、迁移、原子提交、导入导出、历史索引。 | 版本、写者代号、旧修订号一起比较才提交。 |
| `src/ui/` 与 `src/feedback/` | 山门候选、系统全览、宿主私令、公开纪事、回归结算及减弱动态模式。 | UI 提交招募邀请或发令意图。文字、声音和图集消费已提交事实，跳过或重播只改阅读状态 |

首屏先读最近已提交的摘要。Worker 在后台补算，按完成批次推送新修订。界面只保留投影，可在 Worker 重启后按修订重建。用 Vite 的模块 Worker、Dexie 事务与标准 Web Audio。不另建 ECS、服务端编排器或行为树编辑器。[Vite](https://vite.dev/guide/features.html) · [Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers) · [Dexie](https://dexie.org/docs/Tutorial/Design)

## 宿主、任务与奖励

**成员与知情范围。** 候选名帖来自真实地域、来历、试艺和赴约意愿。一届候选无放回，翻页和重开沿用原来的人。正式入宗产生 `member.joined`，同事务建立唯一绑定，才允许对该人派令。全宗在籍成员均已绑定，外出和分院仍属于本宗。退宗停止收新令，保密约束和既有经历保留。重入宗沿用原人物身份。

| 谁在读 | 能读到什么 | 例子 |
| --- | --- | --- |
| 玩家作为系统 | 各宿主的私令、奖励、进度和关联事实，道源、根基与已解锁权限 | 能在同一场大比看见谁突破、谁获胜、谁护擂，以及三份分别兑现的奖 |
| 一名宿主 | 公开见闻、自己的私令和实际所得。决策只用本人感知、性格、目标、经验和可用资源 | 对手可以看见雷法，却不能读取对方领到《惊雷诀》的私令 |
| 游戏内公众 | 实际入门、成丹、比试、授业等可公开观察的事实 | 擂台上能看到长老收住阵雷、两人平安离场。私令与奖品来由留在各自的私密记录，宿主无法借对话或行为向旁人暗示系统存在 |

**发令。** 玩家点名和默认自动派发使用同一条规则。固定任务实例 `missionId`、受令宿主或宗门范围、可验证目标和达成条件、期限、明奖、预封隐藏奖及其来源。先验证绑定、权限、真实机会和可用资源，再把 `mission.issued` 和物资或道源的预留原子地写入同一修订。以 24 道源悬下耗 6 的灌注为例，发布后可用 18、预留 6。相同发令命令重试只返回原回执，两个许诺不能各占同一枚丹药。

**行动与结算。** 任务可以待回应，宿主可接受或推辞，分别记录 `mission.accepted` 或 `mission.declined` 与作决定时的依据。已接受的任务可完成、失败或到期。宿主依自身意愿备战、炼丹或改走另一条可行路线。实际成丹、胜场或护擂事实符合条件时，形成 `mission.settled` 与 `reward.granted`。一次事务写入任务结果、扣除预留、记入所得并更新人物状态。十轮灌注按约定口径折算，常态每轮 8 缕的宿主实得 80 缕，并可在下一行动使用。推辞或失效时释放尚未兑现的对应预留。

明奖和每份追加奖各有独立兑付标识。比如宿主服丹后立即发主奖，只有这一枚丹帮助这一次冲关成功，才发事先封好的隐藏奖。主奖已结时，隐藏条件仍能引用原任务和服丹事实，等条件成立或对应窗口关闭才兑现或释放其预留。

**权限成长。** 道源承担已许的奖励，道统根基记录真正留下的宗门成就。以原始成就判重，如同一独创丹方首次被第二位弟子独立炼成。反复记录同一首成只返回原有记录。根基跨过当前内容定义的门槛时记录 `system.advanced`。基本任务从初始阶段即会自动派发，随后可设常开悬赏、赐予永久能力、联动多人、发布宗门任务。

**多人和全宗。** 多人任务分别对每个宿主结算，赢擂、提前突破、护住二人各有自己的事实。在「万剑归宗」里，入阁可先结领队私令，第三名符合条件者独立练成才结宗门主奖。冻结任务达成时的在籍名单和每人当时的常态实修量，百轮灌注按人折算。以 `missionId + rewardSlot + recipientId` 唯一入账。即便分批落盘，所有收件人共享同一生效刻，恢复后从持久进度续结。整批入账后再发布可见修订、全宗结算摘要并继续推进后续行动。

## 时钟、随机性与规模

- **同一时间轴。** 首测可取现实一分钟对应一个世界日，一日十二时辰，内部以整数世界刻记录，存换算余数。时间倍率、任务期限与修炼速度分别配置。招来的宿主各有既往积累，短时可见真成丹、首胜和修为灌注。常规大境按世界条件突破，生效的系统例外另记来源。
- **同刻有次序。** 跳到下一件会改变选择的行动。先提交此前排定的世界行动与成员变更，再核验有效任务、结算相应奖励与首成，之后关闭到期的未成任务。截止刻已经完成的行动可计入。接着依命令序号处理玩家意图和自动派令，分配资源并让宿主选择下一步。同阶段按稳定 ID 排序。新令只匹配发布以后符合条件的行动，新奖励从到账后的行动开始生效。持续修炼按区段累计，遇到能改变选择的阈值即分段。
- **随机可复演。** 锁定整数 PRNG 与版本（建议复用 pure-rand 的固定算法并保存测试向量）。由世界种子、领域、稳定机会 ID 和尝试序号派生子流。候选、宿主行为、斗法、生产与措辞各有独立序列。A/B 两档只改一项悬赏目标，已经抽出的候选人、既有装备和无关天时保持可比。排除 `Math.random()`、遍历插入顺序和系统时间等隐性输入。[pure-rand](https://github.com/dubzzz/pure-rand)
- **离线与重试。** 将已结算墙钟水位、对应世界刻、余数和未处理终点一起存档。恢复时以同一算法向前推，后台节流仅影响工作分片。每批原子保存进度。中途退出可续算，重开不重领。时钟倒拨以既有水位为下界。异常向前跳转显示来源和跨度，本地玩法允许分批补算。超长离线也保留剩余区间。补算时新发的任务或新培养倾向排在实际提交对应的时刻，既往胜负、预留与已发奖励保留原样。
- **等价验证。** 相同种子、命令时刻和版本，比较一次推进、随机分片、后台恢复与中途崩溃后的域状态、候选与绑定、私令、预留、库存、奖励、根基、关键事实和随机游标哈希。排除 UI 时间戳、物理分块与测试耗时。相同的无决策日才能合并，需跨阈值则切开。真实关页后重开另测一次，以免虚拟时钟掩盖写盘故障。
- **拓展。** M1 精算本局实际招入的宿主及在场对手，记录测试存档的人数。M3 才引入活跃宗门细算和远方势力按时期结算，输入为库存流、承诺、人口和外交事实。进入关注区前在同一时刻交接人物身份、绑定、资源、未完私令与承诺。热点关系按人物／地点索引，外出只匹配同地候选，不遍历全世界人物对。保留人物出生、传承和去世索引，即使角色退出活跃集合仍可回顾。

## 战斗、经济与事实

先比较境界与有效修为，结合所学功法、装备掌握、伤势、灵力与环境，导出有界优势档。战斗局部状态含主动权、退路、可用技法、已付代价。一次性处理少量有条件的转折。趋势相近时随机性更显著，大境差距下翻盘需要可以指出的例外依据。名册以境界基准加有界的攻势、防护、续航试演分展示常态战力。按玩法例，炼气战力 96 的持剑者可凭真实伤势与克制击败 112 的对手。伤害仍由本战的锋势、灵盾和护甲结算。

一条 `BattleFact` 至少含 `id, tick, actorIds, contextAtStart, seedRef, ruleVersion, causes, turns[], outcome, deltas, afterEffectIds`。每个转折存原因、效果、所用物和展示用的当时名称。公开简报、详报、关联私令与系统回归摘要引用同一 ID，由对应读者的可见范围决定显示内容。账本按 `settlementId + effectIndex` 唯一入账，任务效果同时对应上文的收件人兑付标识。战斗事实、奖励、伤势、关系与新活动要么一起提交，要么都可重试。模板改变时仍须能渲染旧记录的胜负与原始因果。

灵根属性、灵根品级、人物境界、技艺品阶、丹药阶与品、法器阶与品均独立建模。炼气可驱动凡阶法器约半力，筑基才有充分掌握资格。真正器灵只可能来自帝器。修炼消耗时间、可用灵气与资源。生命和材料有来源也有去向。灵石四级分别记整数实物，交易检查对手库存，相邻理论比值 1∶10,000，不能把低阶石合成为高阶石。涉及巨额总值用整数运算，JSON 导出大整数为十进制字符串。系统特例走带 `origin=system` 的明确效果，实物奖励从已预留账户转移，道源的可用与预留额、道统根基和受奖者修为分别入账。

## 存档及数据保护

1. **可携带的存档。** 文件封套包括 `saveId, schemaVersion, rulesVersion, contentVersion, rngVersion, revision, clockAnchor, seed, snapshot, pendingQueue, facts, checksum`。快照保存本届候选、入退宗与绑定、宿主私令及期限、明奖与隐藏条件、预留和已发回执、根基首成、权限、人物记忆与随机状态。群体结算中的收件人快照与进度随档保存。账本按面值。人物和事实通过稳定 ID 连接。URL、文件名及项目显示名不充当主键。
2. **存储和写者。** IndexedDB 分表存元数据、分代快照、事实、账本、命令回执。索引按存档、人物、世界刻和父因。列表游标分页。每批在同一事务中检查旧 revision 和写者代号，提交事实／状态／水位和新 revision。优先用 Web Locks 减少多标签竞争，无该 API 时用数据库内租约和递增写者代号。过期写者不得提交。另一标签可只读旁观。重复命令 ID 直接返回原回执。[Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)
3. **故障与恢复。** 保留最近两代有效快照与覆盖两代间的增量。加载先验完整性、版本和引用。存储满、事务中断或校验失败时停止推进可写水位，显示可导出的最近有效档。保存候选可另槽重试。浏览器清理站点数据可能丢失本地档，提供独立文件导出及恢复入口。[浏览器存储配额](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
4. **迁移与回滚。** 原档先导出，再在新槽按顺序升级，核对人物数、绑定关系、物资、私令、预留与兑付、根基和历史引用后才切换活动指针。未知的更高版本允许原样导出、保留旧槽。为每次已发布版本留最小黄金档，测试升级、失败切回、重复导入。回退程序用上版兼容的备份槽，不能用旧程序覆盖新档。规则升级从明确的提交边界生效，旧战报只读其事实。
5. **长档可查。** 平凡重复劳动按角色和时间段合计。每个关系改变、重大机会、裁决、战斗、死亡和引用着的前因保留可定位摘要。压缩前验证所有 `causeId` 能解析到事实或带原 ID 的归档条目。收藏人物的关键生涯永久保留。先测体积、读取时间和压缩往返，再决定阈值。Git 管代码和小型测试夹具，真实存档用独立文件，素材用外部原库及可恢复备份。

## 实验边界

在基准机上记录人数、时间跨度、事实数、主线程最长任务和恢复耗时。M1 用早期实际招生的存档比较八小时离线补算和在线推进等价性，同时滚动回归摘要。M3 再测百人一天及千人分层。对性能结果标注机型、浏览器、样本量与测试方式。试玩若说不出奖品生效后的变化，先改任务目标、奖励用途或呈现。硬件实测定位到瓶颈后再调整渲染或存储方案。[阶段目标](roadmap.md#长线验证与回退)
