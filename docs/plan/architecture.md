# 技术决策与可验证契约

**采用 Vue 3 + TypeScript + Vite，主要画面使用 HTML/CSS。** 一个独立的纯 TypeScript 模拟内核同时供 Web Worker 和无界面测试使用。Dexie 封装 IndexedDB。首版交付静态站点、设备本地存档和可导入导出的文件。游戏运行没有在线模型调用，也无服务器账单。框架版本在 N0 选兼容的稳定版并锁定。

## 为什么采用这套组合

| 候选 | 对这个项目的收益 | 代价与决定 |
| --- | --- | --- |
| Vue 3 / React | 双方均能把人物志、可变长度战报和政策表单表达成响应式 DOM。浏览器负责中文换行、焦点、缩放和滚动。 | 选 Vue 单文件组件，将表意模板、排版及交互就地维护。状态真相在内核，每个小步无需驱动所有人物组件刷新。若团队以后有实测瓶颈，先量消息／布局成本。[Vue](https://vuejs.org/guide/introduction.html) · [React](https://react.dev/learn/thinking-in-react) |
| 原生 DOM + TypeScript | 依赖最少，适合本轮静态排版校样。 | 长期维护人物筛选、回归摘要、多层钻取与焦点恢复需要手工同步，切片起使用 Vue。 |
| PixiJS | 适合未来大量动态图元、地图或局部高密度演出。 | 首版一张插画、少量头像与偶尔一张图集，CSS 足够。需求出现后只对该图层比较 Canvas2D 与 Pixi 的真机成本。[PixiJS](https://pixijs.com/8.x/guides/getting-started/intro) |
| Phaser / Three.js | Phaser 提供完整二维游戏循环。Three.js 擅长空间场景。 | 首版几乎没有连续场景交互，文字输入、可访问性、长纪事与移动排版仍要 DOM。多维护一套坐标、输入与渲染循环的收益很低。[Phaser](https://docs.phaser.io/phaser/getting-started/what-is-phaser) |

### 模块边界

| 建议目录 | 拥有的数据和接口 | 谁可以改变世界 |
| --- | --- | --- |
| `src/sim/` | 人物、关系、宗门账本、事件队列、随机流、战斗、事件效果。`advance(state, untilTick, orderedCommands)` 产出新的状态与有序事实。 | 只认已验证的命令及到期事件，不依赖 DOM、网络、墙钟或 Vue。 |
| `src/content/` | 版本化条件、效果注册表、场景／角色／模板、事实对应的中短文案。可扩展 `conditionId` 与 `effectId`。 | 数据引用受测的操作，模板无任意脚本入口。素材等级标签不覆盖世界规则。 |
| `src/worker/` | 接收 `AdvanceTo / SubmitCommand / QueryHistory`，管理排序、分段推进、持久化与取消。 | 同一存档单写，广播 `revision + viewDelta`。主线程只取可见人物和分页事实。 |
| `src/storage/` | 存档、迁移、原子提交、导入导出、历史索引。 | 版本、写者代号、旧修订号一起比较才提交。 |
| `src/ui/` 与 `src/feedback/` | 山门、人物志、政策、事件详情。已提交事实的声音、字幕、图集和减弱动态模式。 | UI 提交玩家意图。播放完毕、跳过、重放或加载资源失败都不得回写战斗。 |

首屏先读最近已提交的摘要。Worker 在后台补算，按完成批次推送新修订。界面只保留投影，可在 Worker 重启后按修订重建。用 Vite 的模块 Worker、Dexie 事务与标准 Web Audio。不另建 ECS、服务端编排器或行为树编辑器。[Vite](https://vite.dev/guide/features.html) · [Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers) · [Dexie](https://dexie.org/docs/Tutorial/Design)

## 时钟、随机性与规模

- **同一时间轴。** 首测取现实一分钟对应一个世界日，一日十二时辰，内部用整数刻记录。持久化换算余数，短间隔多次关闭也不会吞时间。开局使用已有修炼经历的角色。修行可能数百年才筑基，首局的收获是调息、经验、小步进展与人情。时间倍率、触发窗和修炼速度是三个可分开调的参数。
- **一次推进到下一件有意义的事。** 只处理到期活动、相遇、事件窗口、命令。并列项按 `tick → phase → stableId` 固定顺序处理，阶段固定为已到期后果、当刻玩家命令、生成人物选择、分配占用。被两人争的药包在一个阶段按明确优先级判给一方，另一方重新选活动。记录分配理由。持续动作按区段累计，到能改变选择的阈值时才重新调度。
- **随机可复演。** 锁定整数 PRNG 与版本（建议复用 pure-rand 的固定算法并保存测试向量）。由世界种子、领域、稳定机会 ID 和尝试序号派生子流。世界事件、战斗、措辞各有独立序列。A/B 两档同源，改一条政策不会凭空洗掉整个世界的抽签。排除 `Math.random()`、遍历插入顺序和系统时间等隐性输入。[pure-rand](https://github.com/dubzzz/pure-rand)
- **离线与重试。** 将已结算墙钟水位、对应世界刻、余数和未处理终点一起存档。恢复时以同一算法向前推，后台节流仅影响工作分片。每批原子保存进度。中途退出可续算，重开不重领。时钟倒拨以既有水位为下界。异常向前跳转显示来源和跨度，本地玩法允许分批补算。超长离线也保留剩余区间。补算时新增政策排在其提交对应的时刻，不能追溯改变已发生的事。
- **等价验证。** 相同种子、命令时刻和版本，比较一次推进、随机分片、后台恢复与中途崩溃后的域状态、库存、关系、关键事实和随机游标哈希。排除 UI 时间戳、物理分块与测试耗时。相同的无决策日才能合并，需跨阈值则切开。真实关页后重开另测一次，以免虚拟时钟掩盖写盘故障。
- **拓展。** M1 实算六人。M3 才引入活跃宗门细算和远方势力按时期结算，输入为库存流、承诺、人口和外交事实。进入关注区前在同一时刻交接人物身份、资源与承诺。热点关系按人物／地点索引，外出只匹配同地候选，不遍历全世界人物对。保留人物出生、传承和去世索引，即使角色退出活跃集合仍可回顾。

## 战斗、经济与事实

先比较境界与有效修为，结合所学功法、装备掌握、伤势、灵力与环境，导出有界优势档。战斗局部状态含主动权、退路、可用技法、已付代价。一次性处理少量有条件的转折。趋势相近时随机性更显著，大境差距下翻盘需要可以指出的例外依据。综合战力用分段／对数映射显示，保留境界标签与影响因素。它不参与反推货币、寿元或稀有概率。

一条 `BattleFact` 至少含 `id, tick, actorIds, contextAtStart, seedRef, ruleVersion, causes, turns[], outcome, deltas, afterEffectIds`。每个转折存原因、效果、所用物和展示用的当时名称。简报、详报和双人关系条读取同一 ID。账本按 `settlementId + effectIndex` 唯一入账。战斗事实、奖励、伤势、关系与新活动要么一起提交，要么都可重试。模板改变时仍须能渲染旧记录的胜负与原始因果。

灵根属性、灵根品级、人物境界、技艺品阶、丹药阶与品、法器阶与品均独立建模。炼气可驱动凡阶法器约半力，筑基才有充分掌握资格。真正器灵只可能来自帝器。修炼消耗时间、可用灵气与资源。生命和材料有来源也有去向。灵石四级分别记整数实物，交易检查对手库存，相邻理论比值 1∶10,000，不能把低阶石合成为高阶石。涉及巨额总值用整数运算，JSON 导出大整数为十进制字符串。系统特例走带 `origin=system` 的明确效果，普通发奖从已知预算或实物账户转移。

## 存档及数据保护

1. **可携带的存档。** 文件封套包括 `saveId, schemaVersion, rulesVersion, contentVersion, rngVersion, revision, clockAnchor, seed, snapshot, pendingQueue, facts, checksum`。快照保存私密委托、预留库存、人物记忆、事件冷却和随机状态。账本按面值。人物和事实通过稳定 ID 连接。URL、文件名及项目显示名不充当主键。
2. **存储和写者。** IndexedDB 分表存元数据、分代快照、事实、账本、命令回执。索引按存档、人物、世界刻和父因。列表游标分页。每批在同一事务中检查旧 revision 和写者代号，提交事实／状态／水位和新 revision。优先用 Web Locks 减少多标签竞争，无该 API 时用数据库内租约和递增写者代号。过期写者不得提交。另一标签可只读旁观。重复命令 ID 直接返回原回执。[Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)
3. **故障与恢复。** 保留最近两代有效快照与覆盖两代间的增量。加载先验完整性、版本和引用。存储满、事务中断或校验失败时停止推进可写水位，显示可导出的最近有效档。保存候选可另槽重试。浏览器清理站点数据可能丢失本地档，提供独立文件导出及恢复入口。[浏览器存储配额](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
4. **迁移与回滚。** 原档先导出，再在新槽按顺序升级，核对人物数、物资、账本、关系、待结算与历史引用后才切换活动指针。未知的更高版本允许原样导出、保留旧槽。为每次已发布版本留最小黄金档，测试升级、失败切回、重复导入。回退程序用上版兼容的备份槽，不能用旧程序覆盖新档。规则升级从明确的提交边界生效，旧战报只读其事实。
5. **长档可查。** 平凡重复劳动按角色和时间段合计。每个关系改变、重大机会、裁决、战斗、死亡和引用着的前因保留可定位摘要。压缩前验证所有 `causeId` 能解析到事实或带原 ID 的归档条目。收藏人物的关键生涯永久保留。先测体积、读取时间和压缩往返，再决定阈值。Git 管代码和小型测试夹具，真实存档用独立文件，素材用外部原库及可恢复备份。

## 实验边界

首轮只比较一次 Worker 补算与 UI 同时滚动的实测，记录机器、浏览器、人数、时间跨度、事实数、主线程最长任务及恢复耗时。M1 用六人离线八小时作为门槛，M3 再测百人一天与千人分层。试玩未通过时优先修决策可读性、人物选择或后果密度。只有在设备测量定位到现有方案的瓶颈后，才考虑更换渲染器或存储结构。
