# Neon 的协作与验收规则

每项工作只指定一个实现负责人。当前交付围绕“随机招徒 → 绑定宿主 → 系统派令 → 放置达成 → 实奖到账”。目标、边界与验收从当前开工单领取，具体解法交给实现者。经确认的世界规则、存档兼容、素材来源及事件事实具有约束力。[Neon 开工入口](README.md)

## 最小团队

| 使用谁 | 什么时候值得用 | 输出及停止条件 |
| --- | --- | --- |
| Neon | 选择眼下最重要的玩家问题、拆一张工单、协调工作树、独立复玩或安排验收。 | 一个范围、一位实现者、一次验收结论。参与写实现时，换另一位做独立验收。 |
| Hydrogen | 默认实现者。连通内核、UI、存储和真实入口，修复普通 Bug。 | 小步提交、能复现的种子或操作、修改前后证据。简单任务可独自完成再交 Neon。 |
| DeepSeek | 接口已定、输入能单独交付的工作，如内容 lint、批量夹具、CSV 映射、统计偏差或旧档回归。可替代 Hydrogen 做一张独立票。 | 返回数据、测试或补丁。批量文案抽样读前因与后果。共享核心文件仍由一位负责人修改。 |
| 一位高级模型 | 相同缺陷经过两种有记录的修法仍复发、跨模块确定性失效、旧档损坏风险、高影响架构争议或两轮切片仍无法产生有分量的选择。 | 只请一位给根因／取舍及可证伪预测。Astra 可做设计复核，Argon/Opus 任选其一看关键难题。Carbon 等付费 API 仅在具体任务有优势且本次预算已获授权时使用。 |

以上人选来自原规划登记的资源，执行时按当前平台确认实际可用人选、权限与余额。默认一名写代码、一名验收。确有互不相交的任务才让第二名实现者开独立工作树，同时活跃实现者最多两名。Neon 验明任务入口才派工。豆包上的 Kimi／DeepSeek／Qwen 可替代独立小票，不叠加常设岗。GPT Plus／Claude Pro、少量 Argon/Opus 保留给关键复核。Vertex 的 429 和远端模型均不进入游戏运行依赖。

每张任务单传目标、范围、版本、相关文件、一个失败样例、完成标准和回退点。起步约一页上下文、3～5 个必读文件，需要更多时指出依赖。每项付费调用预先记上限、预计次数、停止条件和替代路径。历史素材盘点记录免费探测。曾提及的账户余额与本次任务获准支出分别记录。没有跨平台调用能力时，Neon 在仓库落任务单与基线提交，由可访问该平台的人转交，再收回分支／补丁、测试命令和证据路径。未实际收到结果的工单标记“待转交”。

## 让反馈跟着事件走

每项可见交互在工单登记事件 ID、读者、反馈渠道、理由与素材来源。玩家点「发布」提交意图，内核确认后才显示相应系统消息。下面的 ID 供实现和复玩对齐。

| 已提交的事实 | 谁看见、呈现什么 | 为什么这样呈现 |
| --- | --- | --- |
| `member.joined` / `mission.issued` | 系统看到入门与发令。新宿主只读自己那道“【叮！系统发布任务】”、目标、期限及明奖 | 收到的第一令应让玩家看懂，为什么自己招的这个人值得押上重赏。公开邀请和私下入门提示有明确边界 |
| `mission.settled` / `reward.granted` | 同一个收件人的完成与到账可合成一条提示。正文给真实产物、功法或修为前后值，点击只展开依据 | 宿主炼成才发奖。玩家离线时奖励已经入账，重复查看维持同一笔结果 |
| `system.advanced` | 只有玩家得到进阶提示，能从新开放的权限发起下一项操作 | 道源增长和根基跨档在界面上分清。全宗的公开名望有自己的来由 |
| 战斗或多人任务的关联事实 | 公共战报呈现交锋和胜负，私令分别写各自的赏，系统全览能沿因果展开 | 同一场大比可以有数名履约者。旁人看到雷法，私下赏给谁的《惊雷诀》只向有权者呈现 |

需要音效时先检索本地库，试听并登记候选。缺口再依次使用 sfx 搜索、Soundza 搜索及经授权的生成。视觉优先取既有图集，必要时再用 Arcadia 或 AetherFX。记录实际工具输入、返回 ID 或错误及素材适用范围。已提交事件以 `factId / cueId / assetId / offsetMs / licenseRef` 调度文字、声音和图集。普通任务以文字即可完整表达。重要突破可用一次短声与可跳过的短效果，静音、减弱动态、切后台和略过演出都要可读。离线百余次结算在归来时合并，玩家可主动展开其中一次。核对实际帧表、音画起点与授权，建议同步误差不超过 100ms。[素材与历史探测](assets-tools.md) · [浏览器音频条件](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

## 交接证据

当前实施与放行统一以路线图的 Markdown 工单为准。Neon 从可复现的候选构建进入，实际派令、关页、重开、查奖、再派令。实现者在交接记录里给出下列材料的可打开路径、对应提交和生成方式。[M1 开工单](roadmap.md#m1-开工单) · [M1 验收](roadmap.md#m1-验收)

| 带什么来 | 独立者怎样核对 |
| --- | --- |
| 启动入口与构建记录 | 在第二工作副本按说明启动。登记提交、锁文件、依赖版本、构建和测试命令、结果及访问地址 |
| 同一初态与两份真实游玩导出 | 记录 `seed, startHash, commonInputsHash, rulesVersion, contentVersion, rngVersion, endTick`。起点含同一名正式绑定、可炼丹也可赴擂的宿主。两档只替换一条发令命令的目标，其余输入、同一宿主、同一奖额和终点时刻相同。计算共同输入哈希时只屏蔽该目标。保存原档、命令与结束档供复演 |
| 派令及结算链 | 从 `missionId`、宿主和奖励预留一路追到成丹或真实胜场、`reward.granted`、账本差额及后继机会。分别核实实物、修为、道源和根基。用失败、推辞、到期的记录核实释放预留，用重复打开和重试核实同一奖励只入账一次 |
| 实际 UI 与离线证据 | 保留桌面和手机宽度下当前产品的两张截图、浏览器操作 trace、关页与恢复的墙钟记录。记录系统全览、宿主自己的消息和公开纪事三种视角的结果。另列加速八小时及故障恢复样本，记清真实等待与模拟时间 |
| 无人操作与独立试玩 | 从无人干预的同一初态确认自主修行、自动任务和归来摘要。独立者再从实际用户入口试玩，写下看到的条件、奖品和下一次想养的人。真人观察保留原话、发生位置和未通过项 |

存档、回执与截图须能彼此追到同一个构建和真实事实。源头条件、父因或入账去向对不上时，保留失败档，回到产生该事实的工单修复。实现者和验收者分开记录“规则验证通过”“已独立复玩”“已观察真人体验”。

## 历史资料

归档的 [M1-valley 工单](neon-m1.json) 与 [专用检查器](../../tools/check-handoff.mjs) 检查的是旧药谷方案，程序固定读取 `reliefRun` 和 `surveyRun`。独立复验那份旧工单时，从仓库根运行 `node tools/check-handoff.mjs docs/plan/neon-m1.json --accept`。回归旧检查器本身用 `node --test tools/check-handoff.test.mjs`。上一轮留下的两张图片是静态排版证据。现行宗门系统 M1 的结论取自本页的任务证据、路线图验收及实际复玩。

## 在开发中落地

| 自动化负责的事 | 由谁、何时、怎样确认 |
| --- | --- |
| 缺字段／资源／译文、引用断裂、罕见规则漏条件 | 内容提交即跑 Schema、引用和正反例。首版可用 JSON Schema + Ajv。现有表只加内容，新增操作需附规则测试。[Ajv](https://ajv.js.org/guide/getting-started.html) |
| 负库存、重复发奖、乱序、离在线不同、迁移损失、战报不符 | PR 跑 Vitest 的固定种子、历史黄金档及性质测试。随机失败保存最小种子与命令。概率分布每天或合并前批跑，区分规则故障和体验调参。[Vitest](https://vitest.dev/guide/) · [fast-check](https://fast-check.dev/docs/introduction/) |
| 入口断、掉帧、渲染错误、移动溢出、反馈打断模拟 | Playwright 从正式启动入口跑导航、读档、随机招生、派令分支、离线归来、账本与反复展阅。留 trace、两尺寸截图、控制台／网络错误和耗时。构建成功后再用产物重走主路径。[Trace Viewer](https://playwright.dev/docs/trace-viewer) |
| 玩家记得自己给谁发了什么、哪份赏改变了下次选择吗 | 独立验收者先盲玩再看初态。记录玩家指认的那条私令、到账后实际使用的本事和下次招徒意愿。真人回访按路线图记录，测试绿灯只代表已覆盖的规则。[验收条件](roadmap.md#m1-验收) |

**仓库接力。** 当前任务读路线图的 N0～N4，证据索引随每次实现提交，架构决定在对应文档，失败复现和下一项优先工作随任务提交。正式开发后，Neon 维护一张短状态表（最近稳定提交、当前票、已知问题、下一票）和按票归档的证据。同一信息只维护一份。交接用“提案／已读／已装／已调用／已实现／测试通过／独立试玩／真人观察”标明事实等级，可直接链接文件、日志、截图或原话。设备、时间倍率、种子、规则版本和提交写进证据。

**修复与回退。** 实现者先最小复现、修复、复测原种子和邻模块。同一原因复发则暂停扩张。重大改架构需记当前瓶颈、候选收益、代价、失败门槛和回退提交。每个独立功能测试后提交，整合前 Neon 核对分支与工作树。保持用户现有改动和备份。存档迁移、依赖升级和批量资源操作前另存可恢复的检查点。稳定版本的 Git 引用、旧档和素材来源均需保留。体验刚好过线时也无需例行再找几位高级模型重审。

**备份责任。** 新增或替换资产包时，素材维护者更新包哈希和来源，独立介质备份后抽取一个文件验证可恢复。配置分开保存可提交的默认项及私有本机项。凭据交由原有凭据管理方式保管。每次改档前留一份旧版可导入的独立导出，升级后用新槽演练一次。交接表只记备份位置或凭据引用，不写密钥和真实玩家存档内容。
